# E-18 — Recuperar necesidades emitidas por Menu

## Endpoint versionado

`GET /v1/restaurants/{restaurantId}/availability-definitions`

Proveedor: **Menu**. Dirección: **entrada**. Host: el de Menu; no el de otro servicio.

## Autorización y headers

Permiso requerido: `menu:availability:recover` y acceso al restaurante de la ruta. Identidad humana o de servicio autenticada según [política aprobada](../../02-convenciones.md). Sin credencial válida: 401; sin permiso/ámbito: 403. `Authorization: Bearer <credencial>` y `Accept: application/json`.

## Parámetros

Cada parámetro entre llaves en la ruta es string opaco obligatorio, no vacío. IDs deben pertenecer al restaurante. Versiones se codifican como segmento URL, preservando zona y contador. Query: cursor y limit como E-01.

## Body

Sin body. Un cuerpo en GET se rechaza con 400.

## Respuesta

`200` con `Content-Type: application/json`. Esquema: [NeedsPage](../../schemas/NeedsPage.schema.json).


```json
{
  "items": [
    {
      "availabilityKey": "ak-1",
      "definitionRevision": 1,
      "withdrawn": false,
      "items": [
        {
          "inventoryItemId": "i-agua",
          "quantity": "1",
          "unit": "unit"
        }
      ]
    }
  ],
  "nextCursor": null
}
```

## Comportamiento y errores

Entrada excepcional para Inventory después de pérdida de suscripción. Recurso es la definición plana propiedad de Menu, no una API de inventario. Snapshot consistente con tombstones conservados; eventos concurrentes se concilian por revisión. No inferir retirada por ausencia en una página. Camino normal usa mensajes.

Errores específicos: 409 CURSOR_EXPIRED. Además: 400 formato/headers, 401/403 autorización, 500 INTERNAL_ERROR y 503 MENU_UNAVAILABLE; mutaciones pueden devolver 409 IDEMPOTENCY_CONFLICT y ediciones 412 REVISION_CONFLICT. Todos usan [Error](../../schemas/Error.schema.json), nunca un resultado exitoso vacío para ocultar el fallo.
