# M-03 — Evaluación recibida

**Dirección respecto a Menu:** entrada. **Canal y type versionado:** `inventory.availability.evaluated.v1`.

**Emisor:** Inventory. **Receptor:** Menu. No es endpoint HTTP.

## Autorización

ACL del broker permite publicar solo a la identidad del emisor y consumir solo al receptor autorizado para restaurantId. Menu contrasta producer con identidad autenticada. Consumidores configurados se registran por identidad de servicio, no por un replyTo enviado en datos. 

## Payload completo

Esquema: [EventM03](../../schemas/EventM03.schema.json). Envelope y data son obligatorios; correlationId es opcional y causationId no forma parte de esta revisión. Ejemplo JSON válido:

```json
{
  "messageId": "msg-m-03",
  "type": "inventory.availability.evaluated.v1",
  "schemaVersion": 1,
  "occurredAt": "2026-09-11T16:00:00-06:00",
  "producer": "Inventory",
  "restaurantId": "r-1",
  "data": {
    "availabilityKey": "ak-1",
    "definitionRevision": 1,
    "evaluationRevision": 8,
    "available": true,
    "evaluatedAt": "2026-09-11T16:00:00-06:00",
    "validUntil": "2026-09-11T16:01:00-06:00"
  }
}
```

## Procesamiento y resultado

Menu acepta solo definición actual, revisión de evaluación mayor y vigencia válida. Duplicado idéntico se ignora; misma revisión con contenido distinto es conflicto. validUntil debe ser posterior a evaluatedAt y al reloj actual para habilitar positivo. Definición retirada/desconocida no habilita. La vigencia del ejemplo no fija SLA. Inventory conserva contador creciente por clave; no se prescribe su almacenamiento. Resultado local: actualizar disponibilidad derivada y, si cambia, M-08. Caída detectada/caducidad/falta de evaluación implica no disponible.

ACK del broker significa entrada persistida/procesada según convenciones, no aceptación de una venta. Error estructural o versión incompatible produce cuarentena durable; fallo transitorio conserva trabajo para reintento. No se define código HTTP para un mensaje.

## Qué significa cada referencia

| Campo | De dónde sale | Intención |
| --- | --- | --- |
| availabilityKey | Menu la crea al definir necesidades y la entrega en M-01 | Identifica qué lista se evalúa. Menu sabe qué variante/opción representa, Inventory no necesita saberlo. |
| definitionRevision | Menu la incrementa al cambiar o retirar esa lista; Inventory copia la recibida | Responde «¿qué composición evaluaste?». No equivale a la versión comercial del MenuItem. |
| evaluationRevision | Inventory asigna el siguiente número por clave al emitir una nueva evaluación | Responde «¿cuál evaluación es posterior?». Se conserva creciente tras reinicio y cambio de definición. Reentregar el mismo mensaje no la incrementa. |
| messageId | Inventory crea la identidad de esta publicación | Detectar una repetición de entrega del mismo mensaje. No identifica la receta. |
| available | Inventory evalúa los insumos de la definición | Indica si esa lista puede suministrarse ahora, sin reservar existencias. |
| evaluatedAt | Inventory registra cuándo hizo la evaluación | Permite entender la antigüedad del cálculo; no se usa en lugar del contador para ordenar. |
| validUntil | Inventory fija hasta cuándo se puede confiar en esa evaluación | Después de ese instante Menu deja de considerar el resultado positivo. El plazo se configura, no se toma del ejemplo. |
| reevaluationRequestId | Solo si responde a M-04, Inventory copia el identificador de esa petición | Menu reconoce que su petición de recuperación ya fue atendida. Se omite en evaluaciones espontáneas. |
| correlationId | Opcional, se propaga de la operación iniciadora o se crea para seguimiento local | Agrupar registros al investigar problemas. No habilita disponibilidad ni sustituye reevaluationRequestId. |

Ejemplo conceptual: ak-42 conserva su identidad; definición 1 contiene pan y carne. Inventory evalúa esa definición como evaluación 8 y luego 9 por cambio de stock. Al añadir queso, Menu publica definición 2. Un mensaje tardío sobre definición 1 se descarta, aunque tenga evaluación 10. Las evaluaciones sobre definición 2 se ordenan por su propio contador creciente por clave.

La clave no cambia en cada evaluación. Los cambios de cantidades/composición de la misma necesidad incrementan definitionRevision. Si se crea una necesidad lógica distinta (otra variante/opción), se asigna otra clave. Menu conserva esa correspondencia; Inventory copia la clave sin interpretar su texto.

Para una reevaluación, el mismo ejemplo de payload admite además data.reevaluationRequestId="reeval-1". M-04 contiene ese valor y cada respuesta por clave lo copia. Una petición nueva sustituye el identificador pendiente; una respuesta de la petición anterior no desbloquea la recuperación. El ejemplo principal representa una evaluación espontánea y por eso omite el campo.
